# 後台效能改善驗證

日期：2026-11-11。範圍為效能檢查第 4～7 項，並保留前三項的儲存回饋與重複送出防護。

## 已實作

| 項目 | 行為 |
| --- | --- |
| 減少 API 與驗證往返 | `me` 可同時回傳參考資料，省下一次獨立請求。每次實際請求仍驗證 Auth 與即時服事者權限。 |
| 名單摘要與詳細資料分開 | 新版名單使用 `summary: true`，不載入活動回答、接待與接機資料；查看時由 `get_registration` 取得。舊客戶端與完整名單匯出保留原回應。 |
| 儲存後避免再次讀取單筆 | `staff_update_registration_result` 在同一 RPC 交易中回傳儲存後的標準資料與親子資訊。未套用篩選時，名單刷新沿用總筆數；有篩選時重新計數。 |
| 親子查詢 | 名單的兒童姓名與關聯改由同一 RPC 取得，省去第二次姓名查詢。 |
| 資料庫統計 | `registration_statistics` 一次回傳各區、身分、兒童類型、活動回答、資格、接待與接機的聚合計數，不回傳個別姓名或登記 ID。完整報名 CSV 仍使用完整名單。 |
| 瀏覽器運算 | 用 Map 依活動與區索引，以分類計數加權計算費用、成本及補貼；不再逐批下載全部報名資料或反覆搜尋每人的回答。 |

`staff_registration_detail`、`staff_registration_statistics`、`staff_update_registration_result` 都檢查有效服事者與初始密碼狀態。新增 RPC 僅授權 `service_role`，不開放 `anon` 或 `authenticated` 直接呼叫。

## SQL 實測

環境為本機 PostgreSQL 17 的隔離資料庫 `ictc_performance_check`。從既有本機測試資料庫複製，補齊目前 migrations；未修改遠端測試站或正式站。

執行 `supabase/testing/benchmark-staff-performance.sql`：10,000 筆虛構登記、12 個已公開活動、120,000 筆活動回答，測試交易最後回滾。

| 量測 | 結果 |
| --- | ---: |
| 新聚合函式 `EXPLAIN (ANALYZE, BUFFERS)` 執行時間 | 347.354 ms |
| 同一交易第二次呼叫並序列化聚合結果 | 286.887 ms |
| 聚合 JSON 大小 | 7,078 bytes |
| 完整資料 JSON 模擬基準 | 7,868,902 bytes |

完整資料基準包含登記基本欄位與每筆活動回答，未包含所有正式 API 欄位、HTTP 標頭與壓縮，供比較傳輸量；不是舊版端到端耗時。測試過程發現逐筆活動資格子查詢會造成額外成本，最終改成集合 JOIN，未修改資料庫的全域 JIT 設定。

這些結果是單次本機工作負載，不能推論測試站真實網路、冷啟動或 Auth 延遲，也不是百萬筆資料庫負載測試。

## 驗證方式

- `node --test supabase/functions/staff/helpers.test.mjs`：13 項通過，包含親子姓名與關聯只需一次請求、失敗回傳及既有輸入驗證。
- `node scripts/test-e2e.mjs tests/staff.spec.mjs --workers=4`：286 項通過、18 項略過、0 失敗，耗時 3.3 分鐘。略過項目為非桌面 Chromium 不重複執行的 CSV 案例。後台跨瀏覽器回歸包含費用、成本、補貼、兒童、活動資格、親子導覽及匯出；新增案例確認合併初始化、單筆按需載入、較慢的舊查看請求不會蓋掉新開啟的登記、儲存結果重用，以及統計不下載完整名單。
- 百萬筆案例使用聚合回應 fixture，驗證瀏覽器工作量與報名人數脫鉤；不代表資料庫已處理百萬筆資料。
- `supabase/testing/verify-staff-performance.sql`：在隔離本機資料庫驗證有效筆數、未回覆身分、兒童分類、活動資格、詳細資料與親子姓名、儲存後回傳、停權與 RPC 權限。以 `postgres` 與實際 Edge Function 使用的 `service_role` 分別通過。
- `node --check site/admin/staff.js` 與 `git diff --check`。

## 部署相依性

本次僅完成本機程式與驗證，沒有部署、commit 或 push。部署時先套用 `202611110001_staff_performance.sql`，再更新 staff Edge Function，最後更新網站。新前端依賴新 RPC；舊前端的名單完整資料回應仍保留，避免後端先更新時中斷使用。

遠端後台 API 的完整請求耗時，以及同一次真實身分修改對應的 SQL 量測，尚未執行；上述本機 SQL 與瀏覽器攔截測試不能代替它們。
