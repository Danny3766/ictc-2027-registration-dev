# 大會匯入狀態調整

決策見 [需求討論與決策紀錄](需求討論與決策紀錄.md)「2026-11-11 大會匯入狀態調整」。

## 部署

1. 執行 `supabase/migrations/202611110002_conference_import_status.sql`。首次初始化只設定 category 為 meeting、台灣日期為 2027-02-20 或 2027-02-21 的活動，不更新任何登記的匯入狀態；確認只有兩天特會被勾選。
2. 更新 `supabase/functions/staff/index.ts`。不需更新 registration Edge Function。
3. 更新前端，管理員在活動表單可調整「影響大會匯入狀態」。新活動預設不勾選。舊版前端未傳此欄位時保留原設定。

新前端依賴新資料庫欄位，須依序部署。本次未部署遠端環境。

## 驗證

- 隔離本機 PostgreSQL 17 資料庫依序套用至本 migration，初始選中兩筆活動。
- `supabase/testing/verify-conference-import-status.sql` 通過，測試交易回滾：非大會活動回答正常儲存且不觸發、勾選活動回答觸發、未回答補不參加、改回原值不還原、待匯入保持、身分切換、活動改名與勾選切換、成本不觸發；新增活動預設不勾選、可儲存勾選且不觸發；公開頁同樣只有勾選活動回答觸發。`verify-activity-fields-and-permissions.sql` 另驗證 anon 不能呼叫 `conference_choices`。
- `supabase/testing/verify-staff-performance.sql` 通過，涵蓋儲存結果、詳細資料、統計與權限。`verify-hosting-general-only`、`verify-identity-badges`、`verify-independent-identity-prices`、`verify-unified-identity` 也通過。
- 原有 7 支過時 verify 腳本已依 [資料庫驗證腳本維護](資料庫驗證腳本維護.md) 整理：6 支保留修正，舊 meal-pricing 腳本移至 historical，有效欄位及權限案例由 `verify-activity-fields-and-permissions.sql` 接手，後台報名對象限制及「先開放後限定」案例由 `verify-activity-audiences.sql` 接手。
- 整理後 13 支現行相關 SQL 在本機完整批次通過並回滾；新增公開與後台各 5 個接待單欄異動案例，涵蓋開家回答、接待對象、接待人數、接機回答及人數，且保留最後匯入時間與操作者。
- staff helpers 13 項通過；JavaScript 語法檢查通過。
- 後台 desktop Chromium 77 項通過，含新增的活動勾選欄位案例；該案例在四種瀏覽器皆通過。

以上 SQL 使用本機虛構資料，不能代替部署後的真實大會匯入驗收。

## 2026-11-27 活動改時間不觸發

決策見[需求討論與決策紀錄](需求討論與決策紀錄.md)「2026-11-27 活動改時間不觸發重新匯入」。

### 部署

執行 `supabase/migrations/202611270001_activity_time_no_reimport.sql`。它只取代儲存活動時判斷匯入狀態的資料庫函式，不更新任何登記的匯入狀態。前端與 Edge Function 不需重新部署，也沒有部署順序限制。

### 驗證

- 隔離本機 PostgreSQL 17 依序套用全部 migration 至 `202611240001`。新加的案例「勾選活動改到另一天並改時分」在舊規則下以 `TRACKED_TIME_DIRTIED_IMPORT` 失敗。
- 套用本 migration 後，`supabase/testing/` 下 17 支 `verify-*.sql` 全部通過並回滾。`verify-conference-import-status.sql` 確認新時間已儲存、匯入狀態維持已匯入；改名、切換勾選設定仍觸發。
- 函式權限不變。

### 測試站

2026-11-27 在 SQL Editor 先確認測試站已有活動的勾選欄位，再套用本 migration。接著執行 `verify-conference-import-status.sql`，成功並回滾。正式站尚未套用。
